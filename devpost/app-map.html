JobTrail: app map

A take-home guide to where things live. It's a snapshot generated from commit 6ca1130 (25 Oct 2026), so it can drift as the code changes.

What it is, in four pieces

  • Frontend (frontend/src/): React pages. Each one only talks to the backend at /api, on the same address.
  • Backend (backend/jobtrail/): FastAPI on 127.0.0.1. It does the scanning, rules, AI calls and storage.
  • Local AI: Ollama on 127.0.0.1:11434 (qwen2.5:7b). It only fills three fields for one email at a time.
  • Storage: one SQLite file (backend/data/jobtrail.db; demo mode uses backend/data-demo/). Raw email text is never stored.

One action, end to end: clicking Scan Now

The route: three stops reference route

Search for the anchor in your editor (Ctrl+Shift+F) to jump straight there.

  1. backend/jobtrail/pipeline/rules.py → def classify

    This decides what gets read from headers alone: excluded label, noise sender, rejected sender, don't-track, known platform, trusted sender, hiring-like subject (→ Review), or skip. The AI never makes this decision. KNOWN_PLATFORMS at the top of the file is the Tier A list.

  2. backend/jobtrail/pipeline/gate.py → class Gate / def open

    This is the only code that asks the inbox source for a body. It inserts and commits the access-ledger row, then reads the body. tests/test_gate.py checks that bodies read = ledger rows. That's by design and verified by a test; Python itself can't forbid it.

  3. backend/jobtrail/pipeline/scan.py → def process_opened

    The defence layers in order: detect(body) (before any AI), then llm.extract(visible, header) (strict JSON, validated by Pydantic), then crosscheck(...). Anything suspicious goes to _quarantine, everything else to _store. The if not defences: branch is the demo-only naive path.

The result appears in frontend/src/pages/Tracker.tsx (data from GET /api/applications) and Privacy.tsx (the ledger).

To change this, start here

  • Recognise another recruiting platform: add its domain to KNOWN_PLATFORMS in pipeline/rules.py, and add a fixture plus expectation in fixtures/ (via scripts/generate_fixtures.py).
  • Status wording (e.g. a new way of saying "rejected"): _STATUS_PATTERNS in pipeline/rules.py. The order matters, because rejection is checked first.
  • New injection pattern: INSTRUCTION / MANIPULATION in pipeline/detector.py, with a test in tests/test_detector.py (including a no-false-positives check).
  • A real email source (.mbox import or Gmail): implement InboxSource in sources/base.py (list_headers, _read_body). Nothing else needs to change.
  • UC export wording: ACTIVITY / OUTCOME in backend/jobtrail/export.py.
  • Colours and look: frontend/src/styles/tokens.css. The gauge is SegmentedGauge in components/Gauge.tsx.
  • Local-API protection: check_local_request in backend/jobtrail/main.py, with tests/test_security.py.

A practice to reuse: measure an assumption before building on it

What happened. The plan assumed a hardened "treat the email as data" prompt would help. Before building the defence demo, scripts/model_probe.py tested it against two real models. The hardened prompt alone did not stop the hidden-text attack once the hidden text reached the model.

Where the evidence is. The table in devpost/spec.md → Decisions and Open Issues; the order in process_opened (detector before model); tests/test_defence_demo.py; and pytest -m ollama against the real model.

Reusing it. When a design rests on "the model / library / API will behave like X", write a tiny probe that measures X first, record the result in the plan, and let it decide the architecture. The same habit found the local-API gap at final review, which is now pinned by tests/test_security.py.
